# 长程运行提出的四个要求

上一章说明了哪些任务需要把控制信息移出当前 prompt。这一章回答一个更基础的问题：**一旦移出去，系统就必须满足哪些要求？** 这四条要求不来自 LoopX 的设计偏好，它们来自"运行时间足够长"这件事本身。任何要跨天、跨会话、跨进程运行的系统都会遇到，只是有的系统选择不承认。

## 四个要求

| # | 要求 | 如果不管 | 典型症状 |
|---|---|---|---|
| 1 | 状态必须能脱离上下文存在 | 记忆一断，工作就重复或漂移 | 重启后重做已完成的轮次 |
| 2 | 每次中断必须停在可辨识的位置 | 半成品状态无法判断，重试只能靠猜 | 收费了但说不清结果落在哪 |
| 3 | 同一时刻必须有唯一可问责的行动者 | 两个执行者同时写同一份状态 | 丢失更新、过期持有者继续改 |
| 4 | 消耗必须有上限且可被外部观察 | 空转、重复计费、人被迫一直盯着 | 没人看时无人推进，有人看时热点轮询 |

下面逐条说明：它为什么必然出现，以及如果设计者不正面处理会发生什么。

## 要求一：状态必须能脱离上下文存在

一次会话里，"我说过""我记得""我们刚才决定"是可信的，因为 transcript 还在。长程运行里这三句话全部失效：

- 上下文会被压缩，早期内容让位给近期内容；
- 会话会结束，用户关掉窗口就没了；
- Host 会切换，Codex App 的心跳和 CLI 的一次调用不共享内存；
- 时间会过去，昨天的判断今天可能已经过期。

所以**任何"记住"都必须落在一个不依赖 transcript 的地方**。

不处理会怎样：最典型的表现是重复劳动。Agent 重启后读不到已完成的证据，于是把同一件事又做一遍。第二个表现是漂移——它不再围绕最初的目标工作，因为目标本身已经被压缩出了上下文。

LoopX 对这一条的正面回答是**持久状态 + 只读投影**的分离，这是后续章节的主题。这里只需要记住它的判据：**如果一条信息只存在于 prompt 里，它就不算被记住。**

## 要求二：中断不是异常，是常态

很多系统的设计假设是"运行会正常结束，异常才需要处理"。长程运行里这个假设是反的：

- 进程会被杀（部署、OOM、用户按停止）；
- 网络会断（模型 API、外部服务、Git remote）；
- 人会叫停（发现方向错了、要换需求）；
- 外部条件会挂起（PR checks 没跑完、依赖没发布）。

这些不是边缘情况，它们**在足够长的运行里必然发生**，而且是反复发生。所以恢复不是"出错处理"，是主路径的一部分。

不处理会怎样：系统停在中间状态，而且**没人能判断它停在哪**。是"改完了但没记账"，还是"记账了但没改完"？判断不出来，重试的每个分支都只能靠猜。

这里有一个容易被忽略的推论：**如果中断是常态，那么"完成"就必须是可判定的。** 一个无法被判定是否完成的工作单元，在中途被打断后永远无法安全地继续。这也是为什么 LoopX 要把一轮切成有限个阶段——阶段可枚举，恢复才不需要猜。

## 要求三：行动者必须是唯一且可问责的

只要运行时间够长，就会同时存在多个潜在执行者：

- 多个 Agent 在同一个 Goal 上工作；
- 同一个 Agent 的多个进程实例（重启时的旧进程还没退出）;
- 人工操作与自动化同时进行；
- 换了 Host 之后，旧 Host 还持有旧的判断。

这时会出现一个反直觉的问题：**问题不在于谁工作得更快，而在于谁有权写。**

不处理会怎样：两个执行者都认为自己是当前的负责人，于是同时写同一份状态。结果取决于时序——有时是丢失更新（后写的覆盖先写的），有时是重复 effect（两边都执行了）。更隐蔽的情况是**过期持有者**：一个已经没有权限的执行者，基于过期的判断继续推进。

LoopX 的应对是把"我认为我该做"与"我被授权做"分开：claim、lease、writer fence 这些机制的存在意义，就是让"有权写"成为一个可以被拒绝的状态，而不是一个默认成立的状态。

关键判据：**权限不能由执行者自己声称，必须由一个共享的权威来授予，并且可以被撤销。**

## 要求四：消耗必须有上限且可被外部观察

长程运行会持续消耗两类资源，而且两类都有问题：

**计算与预算。** "还剩多少配额"是减法思维，但一轮合法工作可能根本不需要花费（monitor poll、dry-run），而一次花费也不等于做了有效交付。更重要的是，**没有上限的自主系统最终一定会空转**——它会不断尝试、不断重试、不断"再检查一遍"。

**人的注意力。** 这是更容易被忽略的一类。一个需要人持续盯着的长程系统，实际上并没有实现自动化，它只是把工作从"执行"转移到了"监督"。而当人不再盯着时，系统往往既不会推进也不会停止，只是安静地耗着。

不处理会怎样：两种相反的失败。要么**热轮询**——系统在没有实质变化时反复检查，浪费外部资源和预算；要么**静默停滞**——没有任何机制在无人监督时推进工作，直到有人回来发现什么都没发生。

LoopX 对这一条的应对是三个机制的组合：**准入**（这一轮该不该动）、**backoff**（监测无变化时如何退让）、以及**用 monitor 替代轮询**（由外部条件驱动唤醒，而不是由 Agent 反复询问）。判据是：**没有 delta 就不该花费；而没有外部观察机制的系统，必然退化成人的轮询。**

## 四条要求之间的关系

这四条不是并列的清单，它们有依赖顺序：

```text
状态能持久存在          (要求一，前提)
  → 中断能被识别        (要求二，否则不知恢复起点)
  → 行动者能被约束      (要求三，否则恢复时可能有两个写入者)
  → 消耗能被限制        (要求四，否则系统会自己把自己烧掉)
```

顺序很重要。**没有要求一，要求二无从谈起**——状态都不持久，"停在哪个位置"就没有意义。而没有要求三，恢复本身会制造新问题：两个实例同时尝试恢复同一轮工作。

这也是为什么这些机制在实现上层层依赖：投影建立在持久状态上，恢复建立在阶段划分上，租约建立在共享权威上，准入建立在状态可读上。

## 这些要求从哪里可以得到验证

这四条不是 LoopX 独有的主张，它们是长程系统的通用约束。你可以用它们去审视任何声称支持长程运行的方案，问四个问题：

1. **记忆：** 关掉进程再打开，它能说清刚才做了什么吗？依据是什么？
2. **中断：** 在任意时刻杀掉它，重启后它能判断出自己停在哪吗？还是只能重做？
3. **归属：** 如果两个实例同时启动，谁能写？另一个会被拒绝吗？拒绝的依据是什么？
4. **消耗：** 没人看的时候它会推进吗？没有任何变化时它会停止尝试吗？

这四个问题有可观测的答案，而不是只能靠阅读设计文档相信。

## 本书接下来怎么走

后面的章节按这四条要求组织。每一条都会说明：LoopX 遇到了什么具体问题、选择了什么设计、这个设计付出了什么代价、以及读者可以带走哪条可检查的不变式。

顺序上，先讲要求一和要求二（状态与恢复），因为它们是最底层的前提；再讲要求三（归属）；然后讲要求四（消耗与观察）。第三部分回到"所以你该怎么用、边界在哪"。

## 不变式

1. **只存在于 prompt 里的信息，不算被记住。** 判断依据是进程重启后它是否还在。
2. **如果中断是常态，"完成"就必须可判定。** 无法判定完成的工作单元，被打断后无法安全继续。
3. **权限不能自证。** 由执行者自己声称的权限，在长程运行里等于没有权限。
4. **没有 delta 就不该消耗。** 反过来，没有外部观察机制的系统，会退化成人的轮询。

这四条合起来是对同一个问题的四种追问：**当没人记得、没人盯着、还可能有两个自己在干活的时候，凭什么相信这个系统还在正常推进？**
