# 长程运行提出的四个要求

一个修复任务可能经历代码修改、测试、等待 PR 检查、根据 review 再改、交接给另一个 Agent。每一步都能在一次会话里完成，整件事却跨越了会话、进程和人的决定。

这一章用这个例子引出四个架构问题。它们是理解 LoopX 的阅读框架；不同系统可以选择不同机制，不能把框架本身当成 LoopX 已在所有路径上实现的保证。

## 四个要求

| 问题 | 需要保存或判断什么 | LoopX 的主要处理方式 |
| --- | --- | --- |
| 换会话后怎样接着做？ | 目标、工作项、证据和下一步 | 持久状态与可重建的投影 |
| 执行中断后怎样避免重做？ | 已提交、未执行和结果未知的步骤 | Turn 身份、journal、回执与 provider 读回 |
| 两个执行者同时到场怎么办？ | 各自的工作范围、写入归属和当前版本 | claim、lease、围栏与提交校验 |
| 没有进展时怎样少消耗？ | 预算、可运行工作、等待对象和下一次观察 | quota 准入、monitor、退避与外部调度 |

这些机制共同回答“怎样持续推进”，也允许合法地等待或停止。长时间运行不意味着进程必须一直活着，更不意味着每次唤醒都必须产生交付。

## 要求一：状态必须能脱离当前上下文

修复已经提交，Agent 换了会话。新会话需要知道 PR 的精确标识、对应 commit、哪些检查通过、谁还需要做决定。仅保留“我刚才修好了”无法重建这些关系。

聊天记录可以持久保存，也可以用于解释历史；它仍可能缺少结构、绑定过期输入或被压缩。因此，影响下一步执行的事实需要有可寻址的 owner、版本和读取入口。

LoopX 把 Goal、Todo、Gate、回执等状态外置，再为人、Agent 和调度器提供投影。代价是要维护这些记录和读取成本；收益是换 session 后可以重新判断行动条件。

**使用判断：** 接手者能否从当前事实源确定目标、未完成工作和恢复条件？只出现在当前 prompt 中的信息，不能单独证明持久写回完成。

## 要求二：中断后保留已知事实，也保留不确定性

假设 PR 已推送成功，但本地回执尚未保存，进程就退出了。此时本地缺记录，无法直接推出远端没有发生变化。盲目重试可能重复执行；直接跳过可能漏掉必要的结算。

LoopX 的受治理 Turn 用阶段、身份和回执表达已确认的进展；对 prepared effect 还需要 provider 读回。确认提交则复用结果，确认未提交才可能继续执行，结果未知时保留阻塞与恢复责任。

合法阶段前缀缩小了记录的解释空间，但单靠它不能消除“外部操作已生效、本地 checkpoint 未写”的窗口。恢复能否继续，还取决于绑定身份、授权和外部系统的可观察性。

**使用判断：** 面对一次超时，先查原 Turn 的结果与恢复判定。不要因为调用失败就创建新 identity 重做，也不要将 `unknown` 写成 `false`。

## 要求三：并行工作必须有明确的写入边界

两名 Agent 可以同时修不同模块，也可能争用同一条 Todo。进程重启后，旧实例还可能持有过期判断。因此，“谁负责工作”和“这次写入是否仍合法”需要分别回答。

LoopX 用 claim 表达归属，用 lease 和版本/围栏检查约束适用路径上的写入。检查发生在相应提交边界，旧的显示状态或接管声明不能代替当前授权。

这些机制有配置与迁移边界。默认 legacy handoff 与 `hard_lease` 的要求不同；并非每条 legacy writer 都强制同样的实例围栏。多 peer 并行也不等于全 Goal 只有一个执行者。

**使用判断：** 先确认当前 authority、handoff mode 和 writer 的校验条件，再判断接管能否安全完成。不要把架构目标当成尚未启用路径的保证。

## 要求四：预算与观察要约束无效重复

PR 检查尚未结束时，反复请求模型“再看一眼”可能只得到同一个答案。预算限制总量，却不能独自决定下一轮是否值得运行；有预算也可能应当等待。

LoopX 的准入组合预算、Gate、frontier、能力和工作区事实。预算耗尽会限制正常交付；monitor 用 cadence 和 material-change 判断组织观察，无变化时可以退避或触发重新规划。

Monitor 可以通过受控轮询观察外部状态。有额外事件通道时也可更早唤醒；没有该通道时，退避会增加发现变化的延迟。这是观察成本与响应时间的实际取舍。

LoopX delivery quota 和真实 token、网络、工具费用也需要区分。某次 poll 不记 delivery spend，不代表它没有资源成本。

**使用判断：** 能否看见等待对象、下一次观察时间、预算限制和解除条件？无人关注时，Host 或调度器是否真的仍能触发工作？

## 四条要求怎样组成一个系统

把开头的修复任务走完：

```text
保存 Goal / Todo / 验收条件
  → 当前决策选择可运行工作并检查权限
  → Host 执行、验证、持久写回与结算
  → 等待 PR 检查，按 cadence 或可用事件再次观察
  → 换会话或接管时重读事实、身份与恢复条件
```

这是一次工作流的示意，并非新的状态机或强制 API 顺序。状态让接手成为可能，授权约束谁可以继续，回执帮助判断副作用，预算与观察决定何时值得再动。任何一项都不能独自保证目标成功。
